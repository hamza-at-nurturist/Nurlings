# Proposal

## Why

Each client gets a dedicated server running the full Nurlings stack, managed with Coolify v4.
Today the only supported install is `install-images.sh` plus `docker-compose.images.yml`, which
publishes host ports, expects a hand-made `.env` with six generated secrets, and assumes a host
reverse proxy. A teammate cannot set up a client from the Coolify UI without reading three
documents. We need one Coolify-ready compose file and a short runbook so a new client is "paste,
set a domain, fill a few keys, deploy".

## What Changes

- Add `deploy/coolify/docker-compose.yml`: the published-images stack (Postgres, supervisor, api,
  worker, web) adapted for Coolify. No host ports; one public domain on `web`; public-URL env vars
  derived from Coolify's magic variables; secrets generated by Coolify; images pinned to
  `ghcr.io/nurturist-ai/nurlings/{app,computer}` through a single `NURLINGS_VERSION` variable with
  no default and never `latest`; the Docker socket mounted only on the supervisor; named volumes for
  Postgres and the bot workspaces; healthchecks and `service_healthy` ordering; migrations on api
  start as today; no updater service.
- Add `deploy/coolify/README.md`: server requirements, one-time `docker login ghcr.io` with a
  machine-user token, DNS, Coolify steps, env-var table (required vs optional), upgrade and
  rollback by changing `NURLINGS_VERSION`, Postgres/volume backup and restore, common problems.
- Add a deterministic offline guard test for the new file (see design) so it cannot drift from the
  env list the app reads, pin `latest`, publish a port, or name the upstream.
- Internal identifiers stay as they are (`RAKAZO_*` env keys the images read, `rakazo_app` database
  role, the `web` service name the supervisor looks up). They are not renamed, to keep upstream
  merges small. Image names, domains, database name/user defaults and every value an operator or
  client sees use Nurlings.
- Nothing contacts Rakazo-owned infrastructure. Self-update stays off (`serverSelfUpdate: false`);
  the `updater` image and service are not part of this file.
- One supporting code change: the worker health probe (heartbeat file and `dist/health-check.js`)
  ported from upstream `cc90c276`, worker slice only, because the file needs a worker healthcheck.
- Bot computers get restricted egress by default, and installing the host rules is a mandatory
  setup step, because Coolify servers can host the dashboard and other apps.

## Capabilities

### New Capabilities
- `coolify-deployment`: the contract for the Coolify compose file and its runbook (image pinning,
  routing, secrets, Docker-socket scope, persistence, health/startup order, updater off).

## Impact

- New: `deploy/coolify/docker-compose.yml`, `deploy/coolify/README.md`, one guard test.
- Reads: `packages/brand/brand.json` (registry prefix), `infra/compose/docker-compose.images.yml`
  (source of truth for the app env list), the publish workflow's tag contract.
- Existing `infra/compose/*` install path is untouched and keeps working.
- Operational: clients pin `v0.1.0`, which is cut from `main` after this merges. Until then a test
  deploy uses a `sha-<commit>` tag from a manual publish run (see design).
